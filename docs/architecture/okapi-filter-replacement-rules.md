# Okapi — zasady działania filtrów jako specyfikacja zastąpienia implementacji Java\n\n## Cel\nTen dokument jest specyfikacją behawioralną potrzebną do zastąpienia runtime Okapi/Java implementacją natywną w Pythonie. Przenosimy obserwowalne zachowanie filtra, a nie hierarchię klas Java.\nJava/JVM może pozostać narzędziem referencyjnym podczas reverse-engineeringu i differential testingu, ale nie może być wymagana przez docelowy runtime.\n\n## 1. Ogólny model\nKażdy filtr jest adapterem między formatem dokumentu a neutralnym modelem jednostek tłumaczalnych:\n\nplik wejściowy → reader/parser → struktura dokumentu → eventy + TextUnit + markup + skeleton + metadata → translation engine → target → writer/serializer → plik wyjściowy.\n\nTrzeba rozdzielać: syntax, structure, translatability, markup, skeleton, metadata i serialization. TEXT_UNIT nie oznacza dowolnego tekstu znalezionego w pliku.\n\n## 2. Lifecycle\nLogiczny kontrakt filtra: open(input) → has_next() → next() → ... → close().\nopen() inicjalizuje parser i stan, has_next() sygnalizuje kolejny event, next() zwraca event, close() kończy zasoby. Python może realizować ten kontrakt iteratorem, jeśli zachowane jest obserwowalne następstwo eventów.\n\n## 3. Event stream\nNajważniejszą abstrakcją runtime jest strumień eventów, nie lista stringów. Minimalnie: START_DOCUMENT, TEXT_UNIT, END_DOCUMENT. W zależności od formatu dochodzą zdarzenia strukturalne. Event musi mieć stabilny typ, kolejność, payload, metadata oraz odniesienia do markup/skeleton tam, gdzie są potrzebne.\n\n## 4. TextUnit\nTextUnit jest podstawową jednostką przekazywaną do translation engine. Nie należy redukować jej do text: str.\nModel logiczny: id, source.parts, target.parts, metadata, resource/name, state.\nSource i target muszą być rozdzielone. Jednostka może zawierać wiele części, np. tekst + inline code + tekst. Markup/protected content nie może być bezmyślnie zamieniane na zwykły tekst.\n\n## 5. Markup i inline code\nMarkup należy rozróżniać jako start, end i empty. Dla par należy zachować relację start/end oraz parentage.\nTrzeba zachować nazwę elementu, namespace, atrybuty, kolejność, relacje parent/child, identyfikatory i informacje wymagane writerowi.\nInline code jest szczególnym przypadkiem markup. Może być chroniony, przenoszony przez translator lub dopasowywany source-target. Musi pozostać identyfikowalny podczas round-trip.\n\n## 6. Skeleton i DocumentPart\nSkeleton zawiera dane nieprzekazywane jako zwykły tekst do tłumaczenia, ale wymagane do rekonstrukcji. Nie jest to po prostu tekst pominięty przez parser.\nDla formatów wieloczęściowych trzeba modelować zasoby i relacje między nimi. Przykłady: DOCX — document, headers, footers, comments, notes, relationships; EPUB — wiele XHTML/resources; pakiety ZIP — wiele plików powiązanych relacjami.\n\n## 7. Translatability\nFiltr musi mieć jawne reguły określające, czy dany fragment jest tłumaczalny.\nKryteria mogą obejmować: typ elementu, nazwę elementu, atrybut, wartość atrybutu, kontekst rodzica, styl, właściwości formatowania, stan elementu, konfigurację filtra i typ zasobu.\nPrzykładowo HTML może traktować body, p, span jako tłumaczalne, script i style jako chronione, a wybrane atrybuty jako tłumaczalne zależnie od konfiguracji.\nNie wolno implementować tych zasad jako przypadkowego zbioru if bez testów behawioralnych.\n\n## 8. Protected content\nTreść chroniona nie jest zwykłym tekstem tłumaczeniowym. Typowe przykłady: URL, placeholder, zmienna, wyrażenie, identyfikator, kod, nazwa techniczna.\nLogiczny przebieg: source → segmentacja → translatable fragments + protected fragments → TextUnit.\nPo tłumaczeniu chronione fragmenty muszą wrócić na właściwe miejsce.\n\n## 9. Segmentacja\nTrzeba rozróżniać parse boundary, translation-unit boundary i sentence boundary.\nNie każdy element dokumentu tworzy osobny TextUnit. Granice mogą zależeć od formatu, konfiguracji, elementów blokowych, akapitów i istniejących granic jednostek.\n\n## 10. Metadata\nMetadata nie jest tekstem. Może opisywać źródło fragmentu, lokalizację, styl, identyfikator elementu, właściwości translatability, markup, writer i resource.\nNależy zachowywać metadata nawet wtedy, gdy nie jest widoczna w wyniku.\n\n## 11. Reader\nReader odpowiada za: odczyt, parser składniowy, strukturę, translatability, eventy, TextUnit, markup, skeleton i metadata. Reader nie wykonuje tłumaczenia.\n\n## 12. Writer\nWriter realizuje odwrotność readera: event stream → TextUnit + target → markup restoration → skeleton restoration → serialization → output.\nWriter powinien być deterministyczny. Dla niezmienionego dokumentu read(input) → write(unmodified events) powinno dawać dokument równoważny wejściowemu. Jeżeli format i kontrakt wymagają byte-identical round-trip, test musi wymagać identycznych bajtów.\n\n## 13. Invariants\nKażdy filtr powinien spełniać: brak utraty treści; brak nieautoryzowanej translacji; zachowanie markup; zachowanie kolejności; zachowanie struktury; prawidłowe podstawienie target; brak wymagania JVM.\n\n## 14. Format-neutral execution\nKażdy filtr powinien być adapterem: format parser → format-neutral event/IR → ExecutionService.\nLogika formatu pozostaje w filters/<format>, a execution/ obsługuje wspólny lifecycle, resolver i backend.\n\n## 15. Resolver i descriptor\nResolver nie może opierać się wyłącznie na rozszerzeniu, gdy różne formaty współdzielą suffix.\nDla XLIFF: explicit format/filter_id → suffix candidates → content detection → descriptor.\nDescriptor powinien deklarować: filter_id, format, backend_id, extensions, MIME types, source modes i capabilities.\n\n## 16. Backend\nBackend uruchamia konkretny filtr: NativeFilterBackend → Python filter.\nW przyszłości może istnieć również OkapiBackend, ale ExecutionService nie powinien znać szczegółów żadnego backendu.\n\n## 17. Błędy\nBłędy należy rozdzielać przynajmniej na: INPUT_NOT_FOUND, UNSUPPORTED_FORMAT, INVALID_DOCUMENT, FILTER_CONFIGURATION_ERROR, PARSE_ERROR, WRITER_ERROR, OUTPUT_VALIDATION_ERROR, EXECUTION_FAILED.\nRóżnica w miejscu błędu jest istotna dla reverse-engineeringu.\n\n## 18. Configuration\nKonfiguracja jest częścią zachowania filtra. Trzeba odtworzyć wszystkie opcje, wartości domyślne, precedence, regex, listy/mapowania, reguły ochrony, reguły wykluczania oraz opcje readera i writera.\nSzczególnie ważne jest rozróżnienie: brak wartości != false != pusta wartość, jeżeli implementacja referencyjna rozróżnia te stany.\n\n## 19. XML\nDla XML należy porównywać element przez namespace URI + local name, a nie przez prefix. Prefix może być zmieniony bez zmiany semantyki.\nNależy zachować kolejność child nodes i namespace declarations oraz nie wykonywać arbitralnej normalizacji, jeżeli wpływa ona na kontrakt round-trip.\n\n## 20. ZIP/package formats\nDOCX i EPUB są kontenerami. Należy zachować wszystkie resources, ścieżki, relationships, metadata, content types i strukturę package. Nie wolno traktować ich jak pojedynczego pliku tekstowego.\n\n## 21. DOCX — zakres zastąpienia Javy\nDOCX wymaga modelowania WordprocessingML, nie tylko ekstrakcji tekstu.\nMinimalny zakres: document.xml, styles.xml, numbering.xml, relationships, headers/footers, tables, paragraphs, runs, hyperlinks, bookmarks, fields, drawings, comments, notes, revisions.\nRun musi uwzględniać tekst, style, właściwości, toggle properties, tab, break, no-break hyphen, bookmarks, fields, hyperlinks i markup.\nStyle wymagają rozwiązywania: docDefaults → default style → basedOn → direct formatting.\nJawne false musi pozostać informacją o wyłączeniu, a nie być traktowane jako brak właściwości.\n\n## 22. HTML\nParser musi rozróżniać element, attribute, text node, comment, script, style i doctype.\nInline elements powinny zachowywać się jako markup. script/style są typowo chronione. Wybrane atrybuty mogą być tłumaczalne. Nie należy parsować HTML wyłącznie regexami.\n\n## 23. JSON\nJSON musi być traktowany jako struktura: object, array, string, number, boolean, null.\nTłumaczalne są wybrane string values. Klucze nie powinny być automatycznie tłumaczone. Writer musi generować poprawny JSON.\n\n## 24. YAML\nNależy rozróżniać key, value, sequence, scalar i comment.\nIstotne są quoting, multiline scalar, anchors, aliases i tag types. Jeżeli wymagany jest round-trip formatowania, zwykły dict nie zachowuje wystarczającej informacji.\n\n## 25. Markdown\nMarkdown wymaga rozpoznania paragraph, heading, emphasis, strong, link, image, code span, code block, blockquote, list, table, HTML block i front matter.\nKod i link destinations zwykle wymagają ochrony. Inline markup musi pozostać związany z tłumaczonym tekstem.\n\n## 26. TXT\nNatywny TXT powinien jasno definiować encoding, newline policy, zachowanie pustych linii, trailing newline, whitespace i jednostkę tłumaczeniową.\nDla obecnego projektu kontrakt może traktować cały payload jako jedną TextUnit i zachowywać go bez automatycznego dopisywania newline.\n\n## 27. XLIFF\nXLIFF wymaga rozróżnienia wersji, co najmniej XLIFF 1.2 i XLIFF 2.x.\nW zależności od wersji należy zachować source, target, trans-unit/unit, segment, inline codes, notes, metadata, IDs, state, resname i extension/skeleton information.\nXLIFF nie jest zwykłym XML-em z globalną zamianą tekstu.\n\n## 28. EPUB\nNatywny filtr EPUB musi: otworzyć ZIP; odczytać container.xml; znaleźć package document; rozpoznać manifest; rozpoznać spine; przetworzyć właściwe XHTML/HTML; zachować pozostałe zasoby; zbudować poprawny package.\n\n## 29. Differential reverse-engineering\nJeżeli referencyjny Okapi/Java jest dostępny, należy używać go jako oracle.\nDla identycznego wejścia porównujemy: event trace, TextUnits, markup, metadata, skeleton, output i errors.\nPorównanie wyłącznie końcowego tekstu jest niewystarczające.\nKolejność porównania: liczba eventów; typy; kolejność; source; target; markup; metadata; skeleton; output; błędy.\n\n## 30. Golden fixtures\nKażda odkryta reguła powinna dostać fixture zawierający input, expected-events.json i expected-output.\nNależy szczególnie testować: pusty dokument, Unicode, brak target, pusty target, nested markup, malformed input, protected content, duplicate IDs, brakujące metadata, namespace, newline i trailing whitespace.\n\n## 31. Co trzeba odzyskać z każdej klasy Java\nNie kopiujemy nazw metod. Dla każdego filtra trzeba odzyskać:\n\nInput contract — co czyta, jakie encodingi/resources obsługuje i jakie elementy rozpoznaje.\nTranslatability — co tłumaczy, co chroni, co pomija i kiedy tworzy TextUnit.\nSegmentation — kiedy kończy, scala i dzieli TextUnit.\nMarkup — które elementy są start/end/empty, jak powstają IDs i jak działa matching/parentage.\nMetadata — jakie pola ustawia i jakie są wartości domyślne.\nWriter — jak stosuje target, odtwarza markup/skeleton i serializuje dokument.\nErrors — jakie wejścia odrzuca, jakie błędy generuje i czy może kontynuować.\nConfiguration — wszystkie opcje, defaulty, precedence i interakcje.\n\n## 32. Czego nie przenosić z Javy\nNie trzeba kopiować hierarchii klas Java, interfejsów wymaganych wyłącznie przez JVM, Java-specific dependency injection, Java streams/collections, wyjątków wynikających wyłącznie z implementacji, nieobserwowalnej synchronizacji ani API niepotrzebnego klientowi filtra.\nPrzenosimy semantykę, nie kod.\n\n## 33. Kryterium native replacement\nFiltr jest rzeczywistym zamiennikiem dopiero po przejściu: Java reference → behavioral evidence → explicit rule → regression test → Python implementation → differential verification → native execution.\nSamo przejście testów jednostkowych nie dowodzi zgodności z Okapi.\n\n## 34. Docelowy podział projektu\nimporter/ — analiza JAR + reverse engineering → Filter IR.\nfilters/ — natywne implementacje formatów.\ncore/ — neutralny model dokumentu.\nexecution/ — resolver + backend + lifecycle.\ntranslation engine — praca na neutralnym kontrakcie.\nanalyzer/java_probe/ pozostaje narzędziem badawczym i nie może być zależnością native runtime.\n\n## 35. Najważniejsza zasada\nNie trzeba przepisywać całego Okapi. Trzeba odtworzyć kontrakt: input → parse → classify → emit events → construct TextUnits → preserve markup/skeleton/metadata → accept target → reconstruct → serialize → validate.\nKażda nieudokumentowana reguła tego przepływu jest potencjalnym miejscem niezgodności.\nDalszy reverse-engineering ma produkować: Java behavior → evidence → explicit rule → test → Python implementation, a nie bezpośrednią translację klas Java na klasy Python.\n\n## 36. Priorytet dalszej pracy\n1. wspólny model eventów;\n2. TextUnit/source/target;\n3. Markup/MarkupComponent;\n4. Skeleton/DocumentPart;\n5. translatability;\n6. protected content;\n7. konfiguracja;\n8. reader;\n9. writer;\n10. differential oracle;\n11. format-specific edge cases.\n\nTen dokument jest żywą specyfikacją migracji: każda nowa obserwacja z Okapi powinna zostać dopisana jako jawna reguła i zabezpieczona testem.
